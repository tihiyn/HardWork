# Задание 2

## Первый пример
В процессе тестирования рабочей задачи столкнулся с неожиданным для себя поведением Hibernate. Оказывается, что Hibernate при выполнении flush выполняется SQL-операции не в порядке их описания в коде, а в строго определённом в зависимости типа операции. Конкретно в моём кейсе выстрелило, что любой INSERT выполнится раньше любого UPDATE, хотя порядок в коде обратный.

Порядок выполнения операций при flush описан в документации Hibernate.

## Второй пример
Открыл для себя интересный момент касаемо работы с Spring Data и Hibernate при переезде со 2 версии Spring Boot на 3. В SQL есть операции IN и NOT IN для проверки вхождения/отсутствия значения в заданном списке. Иногда этот список в программе может быть пустым. Но в Postgres нельзя на уровне синтаксиса записать NOT IN (), а NOT IN (NULL) возвращает NULL. В программе был тест, который проверял работу метода репозитория. Этот метод делал выборку из таблицы. Одним из условий выборки было отсутствие значения в передаваемом списке. В данном тесте передавался пустой список. Этот тест на SB2 работал корректно, возвращая ожидаемы записи из таблицы. Но когда я поднял версию SB до 3, то тест упал, так как метод репозитория возвращал пустой список. Видимо, в более старой версии, при проверке наличия элемента в пустом списке, эта ситуация как-то разруливалась внутри (хотя если посмотреть генерируемые запросы в логах, то там именно NOT IN (), что запрещено на уровне синтаксиса Postgres). А в новой версии генерируется запрос NOT IN (NULL), поэтому метод ничего и не возвращал.

В документации описание поведения при пустом списке я не нашёл, только треды пользователей на различных ресурсах.

## Третий пример
Столкнулся со следующей аномалией - при логировании ошибки должно выводиться имя класса ошибки и стектрейс, но в логах было только название (NPE), а стектрейса не было. Из-за этого было не понятно, где искать проблему, а таких ошибок с пустым стектрейсом на проде возникало по несколько сотен в день. К тому же, на тесте ничего не воспроизводилось. Стал грешить на сам логгер, но точно такой же логгер такой же версии используется и в соседних сервисах, где такой проблемы не было. После долгих размышлений, допроса гугла и гпт нашёл, что, если часто возникает одна и та же ошибка в одном и том же месте программы, то JVM "отрезает" stacktrace. Чтобы отключить такое поведение, нужно в параметрах JVM указать флаг -XX:-OmitStackTraceInFastThrow.

public sealed interface ExportResult {
    record Ready(Resource resource, String fileName, long fileLength) implements ExportResult {
        public Ready {
            assert resource != null;
            assert fileName != null;
        }
    }
    record Failed(Reason reason) implements ExportResult {
        public Failed { 
            assert reason != null; 
        }
    }
    enum Reason { JOB_NOT_COMPLETED, FILE_ERROR, JOB_EXECUTION_ERROR }
}
 
// ImportExportProvider
public ExportResult exportData(Long eId, ZonedDateTime s, ZonedDateTime b, String format) {
    try {
        // запуск батч-джобы
        if (ex.getStatus() != BatchStatus.COMPLETED) {
            log.error("Экспорт предприятия с id={} завершился со статусом {}", eId, ex.getStatus());
            return new ExportResult.Failed(ExportResult.Reason.JOB_NOT_COMPLETED);
        }
        // открытие файла
        return ies.buildExportResp(res, f.length(), format);
    } catch (IOException e) {
        log.error("Ошибка при создании файла", e);
        return new ExportResult.Failed(ExportResult.Reason.FILE_ERROR);
    } catch (JobExecutionException e) {
        log.error("Ошибка при выполнении экспорта", e);
        return new ExportResult.Failed(ExportResult.Reason.JOB_EXECUTION_ERROR);
    }
}
 
// ImportExportController
return switch (p.exportData(enterpriseId, begin, end, format)) {
    case ExportResult.Ready ready -> ResponseEntity.ok()
        .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"%s\"".formatted(ready.fileName()))
        .body(ready.resource());
    case ExportResult.Failed failed -> ResponseEntity.internalServerError().build();
};
```

public sealed interface TripPoints {
    record Json(List<VehicleLocationJsonDto> points) implements TripPoints {}
    record GeoJson(Map<String, Object> featureCollection) implements TripPoints {}
 
    static TripPoints empty(Format format) {
        return switch (format) {
            case JSON -> new Json(List.of());
            case GEO_JSON -> new GeoJson(Map.of("type", "FeatureCollection", "features", List.of()));
        };
    }
}
 
// TripProvider
public TripPoints findByPointsInInterval(User u, Long vId, ZonedDateTime s, ZonedDateTime b, Format f) {
    // ...
    return TripsSpan.of(trips)
        .map(span -> pointsWithin(v, span, trips, f))
        .orElseGet(() -> {
            log.warn("Поездки на авто с id={} в промежутке с {} по {} отсутствуют", vId, s, b);
            return TripPoints.empty(f);
        });
}
 
private TripPoints pointsWithin(Vehicle v, TripsSpan span, List<Trip> trips, Format f) {
    // ...
    return switch (f) {
        case JSON -> new TripPoints.Json(filtered.stream()
            .map(loc -> vlm.vehicleLocationToVehicleLocationJsonDto(loc, tz))
            .toList());
        case GEO_JSON -> new TripPoints.GeoJson(vlm.vehicleLocationsToGeoJsonMap(filtered, tz));
    };
}
 
// TripRestController
return switch (tp.findByPointsInInterval(u, vId, s, b, Format.getByValue(format))) {
    case TripPoints.Json json -> ResponseEntity.ok(json.points());
    case TripPoints.GeoJson geoJson -> ResponseEntity.ok(geoJson.featureCollection());
};
```

### Стало:
 
```java
public record TripsSpan(ZonedDateTime begin, ZonedDateTime end) {
    public TripsSpan {
        assert begin != null
        assert end != null
    }
 
    public static Optional<TripsSpan> of(List<Trip> trips) {
        Optional<ZonedDateTime> begin = trips.stream()
            .map(Trip::getBegin)
            .min(ZonedDateTime::compareTo);
        Optional<ZonedDateTime> end = trips.stream()
            .map(Trip::getEnd)
            .max(ZonedDateTime::compareTo);
        return begin.flatMap(b -> end.map(e -> new TripsSpan(b, e)));
    }
}
 
// TripProvider (фрагмент из второго примера)
return TripsSpan.of(trips)
    .map(span -> pointsWithin(v, span, trips, f))
    .orElseGet(() -> TripPoints.empty(f));
 
// внутри pointsWithin
List<VehicleLocation> locs = vlcr.findAllBetween(v, span.begin(), span.end());
```
